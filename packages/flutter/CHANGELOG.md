# Changelog

> This package's unreleased changes and its latest release. Every earlier release is in [`CHANGELOG.archive.md`](https://github.com/jooy2/plass-ui/blob/main/packages/flutter/CHANGELOG.archive.md), and [plass.cdget.com/changelog](https://plass.cdget.com/changelog) shows the whole history on one page. The React package keeps its own at [`packages/react/CHANGELOG.md`](https://github.com/jooy2/plass-ui/blob/main/packages/react/CHANGELOG.md), because the two version independently.

## vNext (2026--)

### Breaking changes

- **A `PlAppLogo` with no `name` needs a `semanticLabel`.** The mark said only what its child said about itself, and an image says nothing, so a logo given `onPressed` was a button with no name. The constructor now asserts that one of the two is given. Pass what the mark says, or `semanticLabel: ''` for a decorative mark, which now takes the mark off the semantics tree, as `alt=""` does on the web.

### Added

- **`PlProgressCircular` takes `diameter`, a number of logical pixels the ring is drawn at instead of `size`'s rung.** The ring's diameters stopped at 32, so a larger ring could only be had by scaling the whole widget, the text beside it included. `diameter: 96` now draws the ring 96 across with the stroke thickened in the ladder's own proportion, the same geometry the React build draws, while `size` still sets the gap and the text beside it. The constructor asserts that it is a finite number above zero, and a ring without it is drawn as before.
- **`PlFilePicker` takes `onAdded`, which hands over what one pick kept and what it turned away together.** `onRejected` and `onFilesChanged` were called one after the other for the same pick and neither knew about the other, so an error shown only when a pick produced nothing usable took state set in one and cleared in the other, relying on an order the docs never stated. `onAdded` is called once per pick `onBrowse` hands back, after the other two, with a `PlFileBatch` of `kept` and `rejected`. A pick that found nothing, and a removal, call nothing.
- **`PlTypography` takes a `headingLevel`, which sets the level the text is announced at without changing the text style `level` picks.** The heading level came from `level` alone, so a line could not keep the `h3` size and be announced as a level-2 heading. `headingLevel: 2` now does that. It works on any `level`, so a `body` line with `headingLevel: 2` is a level-2 heading at the body's size. A value outside 1–6 fails an assert, as it does on `PlAccordion` and `PlDrawer`.
- **`PlDrawer` takes `headingLevel`, so its title sits at the level the screen's outline needs.** It takes `1` to `6` and defaults to `2`, the level the web build already drew the title at, in both modes. Only the semantics change, never the type scale.

### Changed

- **A new `value` makes `PlAnimateCounter` count on from the figure on screen.** It counted from `from` every time, and the frame the new value arrived in drew it at the old count's progress, so a counter that had landed showed the new figure for a frame, dropped to `from` and counted up again. It now counts from the figure the last count landed on, or from the frame a count still running had got to, over the same `duration` with the same `curve`. The first count and a replay, such as a new `play`, still start at `from`, and reduced motion, `paused` and `trigger` work as before.

### Fixed

- **An endless `PlAnimateMarquee` or `PlAnimateLighting` that landed under the setting for less movement and was given a `repeat` while `paused` held it plays that count once the setting is turned off and the pause is let go, as the React build does.** It stood where the new count ends and played none of it. It now keeps the scroll box or the even glow the setting drew while the pause holds, as before, and once the pause is let go it waits out its `delay` and plays the count from the start. Let go while the setting is still on, it lands as before.
- **An endless `PlAnimateMarquee` or `PlAnimateLighting` that landed under the setting for less movement and was given a `repeat` while the setting was on stays where its run ended when it is given `repeat: null` or a new `repeat` after the setting is turned off, as the React build does.** It stood where its run ended once the setting was turned off, but given `repeat: null` it set off from where its passes would have got to since it landed, and given more passes it played them from there. It now stays where its run ended and moves only once it runs again, by a new `play`, a hover or a `visible` trigger seeing it again. One that `paused` held as it was given the `repeat` plays the count from its start once the pause is let go instead.
- **An endless `PlAnimate*` effect that landed under the setting for less movement and was given a `repeat` while the setting was on plays on when the setting is turned off, as the React build does.** It stood on the last frame of the new count and played none of it. It now goes on from where its passes would have got to by then, counting the time it was let go under the setting, and stands on the last frame of the new count only when that time is already past it. One held by `paused` keeps that frame until the pause is let go, and then goes on from where its run stood when it landed. A `PlAnimateMarquee` or `PlAnimateLighting` still stands where its run ended, as its React keyframe lands again under the setting, unless `paused` held it as it was given the count.
- **A `PlAnimate*` effect that finished before the setting for less movement was turned on keeps counting its time through the setting, as the React build does.** Its clock was put back to the end of its run when the setting arrived, so the time between the end of the run and the setting was lost: given more passes or `repeat: null` once the setting was turned off, it went on from an earlier point than the React build, and given more passes while the setting was on, it stood on its last frame once the setting went and played none of them. It now goes on from where its passes would have got to since it began in both cases. One held by `paused` still counts from where its run ended, as before.
- **A `PlAnimate*` effect that landed under the setting for less movement stands at the end of one pass when it is given `repeat: null`, as the React build does.** It turned on from where its passes would have got to, at once when the setting had already been turned off, and as soon as it was otherwise. It now stands at the end of one pass, as the setting shows an endless effect, and turns only once it runs again, by a new `play`, a hover or a `visible` trigger seeing it again. A `PlAnimateMarquee` or `PlAnimateLighting` that ends stands where its run ended rather than starting again from the beginning. A run that finished moving before the setting arrived still turns on from where its passes would have got to.
- **A `PlAnimate*` effect with a finite `repeat` that landed under the setting for less movement stays on its last frame when it is given a new `repeat`, as the React build does.** Given more passes after the setting was turned off, it played them from where its clock had got to since it landed. It now stands on the last frame of the new count, which for an `alternate` run going from `repeat: 1` to `2` is its first frame, and plays nothing until it runs again, by a new `play`, a hover or a `visible` trigger seeing it again. A run that finished moving before the setting arrived still plays the passes a new `repeat` adds, and turns on from where its passes would have got to when it is given `repeat: null`, as before.
- **An endless `PlAnimate*` effect held by `paused` after it landed under the setting for less movement draws where its run stands on the frame the pause is let go.** That frame drew the last frame of the pass it landed on once more, so a `PlAnimateRotate` stood at its `to` angle for a frame before it jumped to where its run stood and turned on. It now draws where its run stands at once.
- **A `PlAnimateMarquee` under the pointer turns into the moving strip at once when the setting for less movement is turned off, as the React build does.** `pauseOnHover` was taken for `paused`, so with the pointer on the marquee when the setting was turned off it stayed the one scrollable copy, and its restart waited, until the pointer left. It now becomes the strip of copies at once, standing where it starts, and once the pointer leaves it waits out its `delay` and moves. Under the pointer the strip still stops where it is, as before.

The wait now goes on, also while there is no line to turn to, and a line already up for its `interval` gives way at once. When taking lines away brings an earlier line back up, that line is held for a whole `interval`, as before.
- **The copies of a `PlAnimateMarquee` after the first keep what they hold when the setting for less movement is turned on or off, as they do in the React build.** Under the setting only the first copy was built, so the others were built again from scratch each time the setting changed, and any widget in them with a state of its own started over. They are now kept, and hidden, while the setting is on.
- **A `PlAnimateMarquee` or `PlAnimateLighting` with a `repeat`, held by `paused` after it landed under the setting for less movement, keeps what the setting showed when the setting is turned off, as an endless one does.** It turned into the clipped strip of copies or the arc at once, while it was still paused. It now stays one scrollable copy, or an even glow, until `paused` is let go, and then stands where its run ended, as before.
- **An endless `PlAnimateMarquee` or `PlAnimateLighting` starts from the beginning, after its `delay`, when the setting for less movement is turned off, as the React build does.** Under the setting the strip stands where it started and the light is an even glow, and when the setting was turned off they jumped to where their passes would have got to by then. Every other endless effect still goes on from where its passes would have got to.
- **A `PlAnimateHeadline` waits only what was left of its `interval` once a pause or a rest off screen is let go.** It waited a whole `interval` again, and before its first turn the whole `delay` as well, so a reel paused or scrolled away just before a line changed held that line for nearly twice as long. A new `interval` or `delay` is now measured from when the wait began, and one the wait has already passed turns the reel at once. A reel its trigger takes back, by turning `play` off or the pointer leaving, waits from the beginning once it is let go again, as before.
- **A `paused` `PlAnimateMarquee` keeps the one scrollable copy it showed under the setting for less movement when the setting is turned off, as the other effects keep what the setting showed.** It turned into the clipped strip of copies at once, while it was still paused, and lost where the reader had scrolled it. It now stays one copy, scrolled where it was, until `paused` is let go, and then moves on.
- **A `PlAnimateMarquee` measures its box for `trigger: visible` and for resting off screen, as the React build does.** It measured the strip inside the box, which is longer than the box by design, so a strip several times the length of its box never had enough of itself in view to meet its `threshold`, even with the whole box on screen, and one whose box had been scrolled out of a row went on moving while the strip past its end still reached into view. It now starts once enough of the box is in view, and rests once none of the box is.
- **What a `PlAnimate*` effect holds keeps its state when the setting for less movement is turned on or off, as it does in the React build.** The widgets above the content changed with the setting, so the content was built again from scratch each time: a field inside a `PlAnimateFade` lost its text, a list its scroll position, and any other widget with a state of its own started over. It now keeps all of it. A `PlAnimateMarquee` was built again as well, so one that had landed under the setting set off on its whole pass again once the setting was turned off. It now stays where it landed, as every other effect does.
- **A `PlAnimate*` effect or a `PlAnimateTyping` built on an app's first frame measures its `delay` from when it began.** The first frame an app draws has no time stamp yet, so a wait begun on it counted all the time the engine's clock had run before the app started. Such an effect paused partway through its `delay` started as soon as it was let go, a `PlAnimateTyping` waiting out its `delay` under the setting for less movement showed its whole line when the setting was turned off, and an endless effect that landed under the setting on that frame went on from the wrong point of its run once the setting was turned off. Each now waits out what is left of its `delay`, or goes on from where its passes would have got to, as an effect built later does.
- **A `PlAnimateTyping` that types its line once keeps the whole line when the setting for less movement is turned off after it has landed, as the React build does.** Under the setting the whole line is shown. When the setting was turned off, the line emptied and was typed again from its first character, or from the character it had reached when the setting arrived partway through. A typing whose `delay` has gone by under the setting, or that was already past its first character when the setting arrived, now keeps the whole line, as an effect that landed stays on its last frame. One whose `delay` is still running when the setting is turned off is empty for what is left of the wait and then types, where it waited the whole `delay` again, and the time a `paused` typing is held is not counted. A typing with a `repeat` of 2 or more, or `null`, types again as before.
- **A `paused` `PlAnimateLighting` keeps its even glow when the setting for less movement is turned off, as the React build does.** Under the setting the light is an even glow, and when the setting was turned off while the light was paused it became the arc at once. It now stays an even glow until `paused` is let go, and then turns as before.
- **A `PlAnimate*` effect `paused` before its `delay` is over keeps what reduced motion showed when the setting is turned off, as the React build does.** Held from the start, or paused while it waited, such an effect shows its content under the setting, and when the setting was turned off it jumped to its first frame while it was still paused: a fade in vanished and a `PlAnimateRotate` turned back from its `to` angle to its `from`. It now stays as it was until `paused` is let go, and then stands on its first frame, waits out what is left of its `delay` and plays, as before. This holds for an effect with `repeat: null` as well, which kept only a frame it had landed on.
- **A `PlAnimate*` effect started again draws its first frame on the frame it starts, as the React build does.** A run started again, by turning `play` off and on, a hover or a new `nonce`, drew the frame the run before it had left for one frame and its own first frame only on the next, so an exit that had landed under reduced motion stayed gone for a frame before it came back for its `delay`, a finished fade stood fully drawn for a frame before it faded in again, and a `PlAnimateCounter` hovered again showed the figure it had landed on before it dropped to `from`. It now draws its first frame at once, paused or not. Under reduced motion a run started again with no `delay` shows its content for that one frame and then lands, as it does when it first appears.
- **A `PlAnimate*` effect started again while `paused` shows its content as it is under less movement until it is let go, as the React build does.** An exit, or an `alternate` effect with an even `repeat`, that had landed under the setting and was started again while it was paused, by turning `play` off and on for one, stayed gone or faded out where the run before it had landed, and so did one started again while paused that the setting arrived on before it was let go. It now stays as it is until `paused` is let go, then waits out its `delay` and lands, or plays when the setting has gone.
- **An `alternate` `PlAnimate*` effect started again while `paused` holds its first frame, as the React build does.** A run with `alternate: true` paused on a pass that ran backwards and started again while still paused, by turning `play` off and on for one, counted a pass as it was put on its first frame and played on while it was paused. It now stands on its first frame until `paused` is let go, and then plays from the start.
- **A `PlAnimate*` effect given a higher `repeat` plays every pass it adds when it stands exactly where a pass begins, as the React build does.** An `alternate` run whose clock stood on the very start of a pass, after a whole number of passes, counted that pass without playing it, so it ended early, on the wrong frame or after too few passes. It now plays on from the start of that pass.
- **A `PlAnimate*` effect given a new `repeat` counts it against the time it has been going, as the React build does.** A run that had finished stayed on its last frame and drew nothing more when it was given `repeat: null` or more passes. It now goes on from wherever its passes would have got to by then, counting the time it was let go after it finished, or from the start of its next pass when it finished while `paused`, and stands on the last frame of the new count when that time is already past it. A run with a finite `repeat` that landed under the setting for less movement is the exception: given a new `repeat`, it stays on the last frame of the new count, or at the end of one pass for `repeat: null`, until it runs again. A run that has played, or is paused, past the end of a lower `repeat` now stands at once on the frame that count ends on, where it played its current pass out first, and an `alternate` one on its way back stopped at its first frame. A pass in flight that the new count still holds plays on as before.
- **A `PlAnimate*` effect paused during its `delay` waits out the rest of it when the platform asks for less movement, as the React build does.** Asked for while `paused` held the wait, it landed at once, so an exit was gone while it was still paused and skipped the rest of its wait, and one given movement back before it was let go never played. It now stays as it was while it is paused, and once it is let go it waits what is left of the `delay` and then lands, or plays when the setting has gone again.
- **A `PlAnimate*` effect waits out its `delay` once while it is built again, as the React build does.** Every build of the widget during the wait, such as its parent setting state, started the whole `delay` again, so an effect whose parent rebuilt more often than its `delay` never started, and one given movement back, or asked for less, during the wait waited all of it again. A rebuild now leaves the wait alone, and a pause still holds what is left of it. A new `delay` is measured from when the wait began, leaving out the time a pause held it, so the wait ends that long after it began, and one the wait has already gone past starts the run as far into it as it would be by now.

- **An endless `PlAnimate*` effect moves again when the platform gives movement back, as the React build does.** Under less movement a run with `repeat: null` stands on the last frame of one pass, and when the setting was turned off it stayed there and drew no frame again, also when it had been moving before the setting arrived. It now goes on from where its passes would have got to by then, counting the time it was let go under the setting, and goes back on every other pass with `alternate: true`. One held by `paused` when the setting goes keeps the frame it landed on until the pause is let go, and then goes on from where its run stood when it landed, which is its first frame for one that landed at the end of its `delay`; one resting off screen is put there at once, and goes on from there once it is back. A run that landed with a finite `repeat` stays where it landed, as before, and one given `repeat: null` afterwards stands at the end of one pass. A `PlAnimateMarquee` and a `PlAnimateLighting` start from the beginning instead, after their `delay`, as their React keyframes do.

- **An `alternate` `PlAnimate*` effect with an even `repeat` stays where it landed when the platform gives movement back, as the React build does.** Under less movement such a run stands on its last frame, the first one, since its last pass runs backwards. When the setting was turned off it played the whole run again and landed there a second time. A run that has landed now stays where it is, as one with an odd `repeat` or without `alternate` already did. One still waiting out its `delay` when the setting goes plays as before.

- **An `alternate` `PlAnimate*` effect with an even `repeat` stays faded out, turned back or wherever it ended when it is built again, as the React build does.** A run with `alternate: true` and an even `repeat` ends on a pass that ran backwards, at its first frame, which is also where a run that has not begun stands. So a rebuild of the widget, such as its parent setting state, played it again and left it at the other end. A run that has finished now stays where it ended. One that has not begun yet, waiting out its `delay` or held by `paused`, still starts as before.

- **An `alternate` `PlAnimate*` effect whose `duration` changes on its way back goes on back, as the React build does.** A run with `alternate: true` given a new `duration` during a pass that ran backwards turned round and ran forwards again, which a `PlAnimateMarquee` with `alternate: true` can meet when its strip is measured again. It now goes on the way it was going, over what is left of the new duration, and turns at the end of that pass as before.

- **A paused `PlAnimateTyping` keeps the whole line it drew under less movement when the platform gives movement back, as the React build does.** It showed the line it had got to at once, while `paused` was still on. It now keeps the whole line until `paused` is let go, and then goes on from that character, or types a line it never began from its first character after the `delay`. One resting off screen, or one its trigger takes back, draws what it did before.

- **A `visible` `PlAnimate*` effect in a `ListView` starts on the scroll that brings it into view.** It was measured as the scroll moved, before the list laid its items out where the scroll had moved them, so an effect the last step of a scroll brought on screen was found where the step before had left it, and waited for the next scroll. It is now measured once the frame is laid out, at most once a frame, as the endless rest already is. In a `SingleChildScrollView`, which was not affected, it now starts and stops one frame later, after the frame the scroll is laid out in.

- **An `alternate` `PlAnimate*` effect paused on its way back goes on back when it is let go, as the React build does.** A run with `alternate: true` held during a pass that ran backwards turned round and ran forwards again when `paused` was let go, and an endless one did the same when it was scrolled back into view. It now goes on the way it was going, and turns at the end of that pass as before.

- **An endless animation rests while it is scrolled out of view, as it does in the React build.** `PlAnimateLighting`, `PlAnimateMarquee`, `PlAnimateFloat` and `PlAnimateBlink`, every other `PlAnimate*` with `repeat: null`, a `PlAnimateAppear` with `repeat: null`, a `PlAnimateHeadline` that loops on its own timer, a `PlAnimateTyping` with `repeat: null` and the typing caret went on drawing a frame or firing a timer for the whole visit wherever they were. Each now pauses once no part of it is left inside the `Scrollable`s above it and the screen, and goes on from the frame, line or character it stopped on when it is back. Finite effects play as before, and so does an endless one hidden some other way, or with no scrollable above it.

- **A `PlAnimateTyping` runs no timers while the platform has asked for less movement, as the React build does.** It drew the whole line then, but went on typing, holding and erasing it underneath, drawing a frame for every character, and one with `repeat: null` never stopped. It now types nothing while the setting is on. Asked for partway through, it shows the whole line and holds where it was; given back, one that repeats goes on from that character, or types a line it never began from its first character after the `delay`.

- **A disabled `PlListItem` that is `selected` sets its label at the weight of a row that is not chosen.** It was drawn without the tint and in the unchosen colour, but its label kept the chosen row's medium weight, where the React row drops `font-medium` with the tint while it is disabled. It is now drawn as a row that is not chosen, whether it has an `onPressed` or not.

- **A `PlAnimateTyping` with an empty `text` runs no timers, as the React build does.** With a `repeat` of 2 or more, or `null`, it typed the empty line, held it and cleared or deleted it again pass after pass, drawing a frame each time, and a `repeat: null` one never stopped. It now draws an empty line and waits for nothing, also when its text is emptied partway through typing, and a `text` it is given later is typed from its first character after the `delay`.

- **A disabled `PlListItem` is no longer announced as selected.** A row with both `selected` and `disabled` said it was selected while it was drawn without the tint, where the React row drops `aria-current` while it is disabled. It now says what a row that is not chosen says, whether it has an `onPressed` or not.

- **A paused `PlAnimateTyping` holds its line when its `text` changes, as the React build does.** Given a new `text` while `paused` was on, it emptied the line, so the pause showed nothing where it was asked to hold what was there. The line on screen now stays as it was until `paused` is let go, and the new text is then typed from its first character, as a new run that arrives while it is paused already is. A screen reader is given the new text whole at once, as before.

- **A paused `PlAnimateTyping` holds its line through a new run, as the React build does.** A new run that arrived while it was paused, such as a `hover` one the pointer left and entered again, emptied the line, so the pause showed nothing where it was asked to hold what was there. The line now stays as it was until `paused` is let go, and the new run then types from its first character.

- **A `visible` `PlAnimate*` effect with a `threshold` of `0` waits until some of it is on screen, as the React build does.** A share of `0` reached a `threshold` of `0`, so such an effect started at once wherever it was, however far below the screen. It now starts when the first of it comes into view.

- **A disabled `PlListItem` that has an `onPressed` is announced as an unavailable button.** It dropped its button semantics while it was disabled, so a screen reader read it as an unavailable row rather than a button it could not press. It is now a button with `enabled: false`, and it still takes no tap and no focus. A row with no `onPressed` is unchanged.

- **A disabled `PlBreadcrumbItem` that has an `onPressed` is announced as an unavailable link.** It dropped its link semantics while it was disabled, so a screen reader read it as unavailable text rather than as a link it could not follow, where the React step that would have been a link is announced as an unavailable link. It is now a link with `enabled: false`, and it still takes no tap and no focus. A step with no `onPressed` and the current step are unchanged.

- **A `PlAnimateTyping` whose trigger has let it go now waits with an empty line.** A `visible` one with `once: false` that left the screen, a `manual` one whose `play` was turned off, or a `hover` one with `repeat: null` that the pointer left went on showing the line it had typed until its next run cleared it. It now waits empty, as it does before it is first let go and as the React build does, and types the line from its first character when it is let go again. `paused` still holds the line where it is.

- **A new `value` no longer starts a `PlAnimateCounter` its trigger has not started, nor a new `text` a `PlAnimateScramble`.** A `manual` counter with `play` off, or a `visible` one not yet seen, started counting as soon as its `value` changed, before it was asked to or where nobody could see it. A new `value` before then only changes what the count arrives at: the counter goes on showing `from` and counts to the new value when its trigger comes, and a scramble's new `text` waits the same way. A counter that has started still counts on from the figure on screen, and `PlAnimateShake` still plays on every new `replay`.

- **A `PlAnimateCounter` or `PlAnimateScramble` that its trigger lets go of waits on its first frame, as the React build does.** A `visible` one that is not `once` and has left the screen, or a `manual` one whose `play` was turned off, held the frame it was on, so a counter showed its old figure while it waited, and on its return drew that figure for a frame before dropping to `from`. A counter now shows `from` while it waits and a scramble its noise, so the next run starts from the frame already on screen. Every other effect still holds the frame it was on.

- **A `PlAnimateTyping` let go during its `delay` or between two characters waits only what was left of that wait.** Paused during the `delay`, or in the wait before the next pass types its first character, it waited a character's time once it was let go, and paused between two characters it waited a whole character's time again. Every wait now goes on with the time that was left of it, as the hold already did, and the two builds wait the same.

- **Moving to another step of a horizontal `PlStepper` builds the new step's panel afresh.** Two panels of the same shape shared their state, so text typed into a field on one step was still in the field at the same place on the next, and so was a scroll position. The panel under the rail is now built anew for each step, as the React panel is; a vertical stepper already was.

- **A `PlAnimateTyping` let go during a hold, or partway through deleting, goes on as it was.** Paused during the hold before `erase` deletes, it started deleting after the typing delay, and paused during the hold between two passes without `erase`, it held for the whole hold again; both now hold for the time that was left of the hold. Let go partway through deleting, it waited the typing delay before the next character rather than the delete delay.

- **Moving to another step of a `PlStepper` from inside its panel puts the focus in the new step's panel, or on the step itself when it has none.** The focus went back to whatever had held it before, often a step behind the reader. The panel that arrives now takes it, and the next Tab goes on to what is in it, in both orientations; a step with no panel takes the focus itself. The panel is never a Tab stop, and a focus elsewhere stays where it is.

- **A `PlAnimateTyping` with a finite `repeat` plays every pass it was asked for when it is paused during the hold between two passes.** The next pass was counted as soon as the line was typed out, before the hold, so a typewriter paused during the hold came back to a pass that was already counted and stopped, and `repeat: 2` without `erase` typed its line once. ## 1.7.0 (2026-09-28)

### Breaking changes

- **`PlChartAxis.grid` is a `bool?`, and a cartesian chart draws its grid and axes as the React chart does.** Left out, `grid` casts rules on the value axis, and on the category axis only when that axis measures, so a `PlScatterChart` now draws its vertical gridlines, as React's does. The pointer pauses it only while it is over the frame, and a reader who asked for reduced motion starts stopped and can start it from the button.

- **`PlassChartSeries.id` is what a chart knows a series by from one build to the next.** It was documented as what identifies a series and read by nothing. A series' legend entry was known by its name and how many series before it have that name, so a series renamed between two builds came back switched on, and when the first of two series with one name left the data, the second took its state over. A series with an `id` keeps its switched-off state through both. A series without one is known as before, and so is a `PlPieChart`'s slice, which has no `id`. The React build makes the same change.

The plot now takes the focus by Tab, with a ring while the keyboard holds it; ← and → walk the categories (↑ and ↓ on a horizontal bar chart and a timeline), `Home` and `End` go to the ends and `Escape` clears the readout, and a scatter, a timeline or a `nearest` tooltip is walked mark by mark in the order the data was given. A heatmap is walked cell by cell, row by row on a grid and largest first on a treemap, and stops at the first and the last; on a grid ↑ and ↓ go to the same column in the nearest row above or below that has a cell, and it has no `Home` or `End` either. Each stop is announced in a live region and the tooltip card stands on it, as in the React build. There is no crosshair with it — a crosshair says "these numbers all belong to this column", and there is no column — and the arrow keys walk mark by mark instead of column by column. It measures to the mark, which on a bar is the bar's data end, and it reads a stacked series where the band was actually drawn rather than at its bare value.

- **A chart legend can fold past `maxEntries`.** A legend is a key, and a key of twelve names wrapped over four rows is a paragraph the reader has to search — on a card it is also four rows the plot no longer has. Past the number given, the rest go behind a button that says how many they are and opens them, with the same button folding them back. The entries kept are the **first** ones, in the order the series were passed, because that is the order their colours were handed out in and a key that rearranged itself as series were switched off would stop being a key. Nothing is hidden from a screen reader by it: the fold is a real button, reachable by keyboard, and every series is in the reading the chart hands over either way.

- **`PlBarChart` takes `sort`, `maxCategories` and `otherLabel`.** A bar chart is the one shape whose categories can be shuffled without losing anything — that is the test for reaching for it over a line chart — so `sort` is free, and it is what turns a wall of bars into a ranking a reader can scan down. `maxCategories` keeps the largest that many and sums the rest into one, which is the answer to a chart of ninety countries: a bar too short to see costs width without saying anything. What is folded is decided by size and never by `sort`, and the fold is always last, because it is not a category but what is left; a fold of nothing but gaps stays a gap rather than becoming a zero. Both are changes to the **data**, so the axis, the readout and the reading a screen reader is handed all agree with the picture about which categories there are — and both happen before a `'full'` stack renormalises, or a category folded away afterwards would have taken its share of every other bar with it. A series hidden from the legend is still counted, because a chart whose columns rearranged themselves when an entry was pressed is one a reader cannot use. The label pack gains `chartOther`, `chartMore` and `chartFewer` in all seven languages.

- **A chart takes `reference`, which draws a target, an average or a limit across the plot.** One line or several, each at a value on the **value** axis — so a reference runs across a vertical chart and down a horizontal one, and a caller who turns a bar chart on its side does not have to move it. It is **not data** and is drawn as if it knows that: dashed, in the muted ink rather than a palette slot, and under the marks, because a reference that looks like a series is one a reader will try to read a value off. `color` takes it to a family where the line means something the page already has a colour for, `dashed: false` makes it solid, and `label` sets a short word at the end of it. Each one is also written into the description a screen reader is handed with the chart, because a target is a fact about the picture rather than decoration on it. On `PlLineChart`, `PlAreaChart`, `PlBarChart`, `PlScatterChart` and `PlTimelineChart`.

- **A value axis can step by multiplying, with `PlChartAxis.scale`.** `log` is the one scale in the library that changes what a distance on the plot means: the same length becomes the same **ratio** rather than the same number of units, so the gap from 10 to 100 is the gap from 100 to 1,000 — which is the only way a series that runs from 3 to 3,000,000 is drawn with the small end still legible. There is no zero on it and nothing below it either, and that is stated rather than hidden: the axis floors at the smallest positive power of ten the data needs, or three decades under the top when the data offers none, and a zero or a negative is drawn on that floor. The ticks are powers of ten, with each decade's 2 and 5 as well over a span of two decades or fewer. It is read on the value axis, and on a category axis only where that axis is a second value axis — a `PlScatterChart`'s. A bar is the wrong mark for it, for the same reason a bar's axis cannot be cropped.

- **A chart's value labels take `valueLabelColor`, for a chart that needs them in the page's own ink.** They are written in their series' colour by default, which is what says which number belongs to which mark. The palette clears 4:1 against the sheet — the floor the design language sets for a chart *mark* rather than the 4.5:1 body text wants — so a chart whose labels have to meet the text contrast rule on their own asks for `PlassChartLabelColor.ink` and gets the page's foreground on every one. On `PlLineChart`, `PlAreaChart` and `PlBarChart`.

- **A chart's category axis can turn its labels, with `PlChartAxis.tickAngle`.** An axis runs out of room across and not down, so a name wider than its slot was cut to it — and past about four characters a cut stops telling two names apart. The axis now takes an angle in degrees, and a turned label takes one line of text across the axis however long it is, spending the room under the plot instead. `-45` is the one to reach for and `-90` stands the names on end. The band under the plot grows to hold them, up to about two fifths of the chart's height; past that a name is still cut, and the readout and the table still have all of it. Only the category axis, and only where it runs along the bottom — a value axis' ticks are numbers already rounded to be short, and a horizontal bar chart's names already have a row each.

- **`PlChartAxis.autoTickAngle` turns the labels only once one of them would be cut.** Upright is the best an axis can do when there is room for it, and a diagonal beats a cut at every width, so it is the setting for a chart whose categories are the caller's data rather than the caller's choice. It settles on `0` or `-45` and never on a third angle: one fitted to the longest name would be a different angle on every chart on a dashboard, and would change under the reader as the window is resized. A sentinel value rather than a second field, because it is the same axis of choice; the React build spells it `tickAngle="auto"`.

- **`PlLineChart` and `PlAreaChart` take `nulls`, which has the answer `connectNulls` could not express.** A missing value means *nothing was measured*, which is a different claim from *nothing happened*, and a boolean only had two of the three replies. `PlassChartNulls.gap` breaks the line, which is the default and what the chart has always done; `connect` joins the two sides, which is what `connectNulls` was; and `zero` reads the gap as a nought — on the value axis, in the readout and in the table under the chart as well as under the line, because a zero is a value and has to be somewhere on the axis. `connectNulls` still works and is read only where `nulls` says nothing, so nothing has to change today; it is deprecated and goes in 2.0.0.

- **`PlPieChart` takes `innerRadius` and `padAngle`.** `shape` picked both — nothing cut out of a `PlPieShape.pie`, a little under two thirds out of a donut and a semi, and a gap of 2px between slices — and neither could be moved. `innerRadius` is a fraction of the radius, so a hole holds its proportion at whatever size the chart is drawn; `padAngle` is in degrees, and widening it is what makes a ring read as separate segments rather than as one band. Left out, both are what they were. A slice narrower than twice the gap still keeps none of it, or a one-degree sliver would invert and draw the whole circle instead of nothing.

- **`PlFloatingActionButton` takes `readOnly`, `density`, `onLongPress`, `focusNode` and `autofocus`.** It passed on only part of what the `PlButton` it wraps takes, where the React build takes all of it. Logical rather than physical, so it turns over under `rtl` and an icon beside the label travels with it.

On `windows7` the buttons hang from the top edge of the bar, and a double tap below them is the bar's.

The bar is now a stop ahead of the window's buttons, named from the new `moveWindow` key in all seven label packs or from `moveLabel`, with a ring while the keyboard holds it.
